# Décisions techniques

Une ligne par décision : date, choix, raison.

- 2026-11-19 : projet calqué sur [Quai](https://github.com/memton80/quai-ssh) — même stack (WinUI 3 non packagé, .NET 10, Windows App SDK 2.6.5 avec les mêmes composants neutralisés, CommunityToolkit.Mvvm, Microsoft.Extensions + Serilog, xunit.v3, Inno Setup, CI GitHub Actions avec test de fumée), même découpage Core / App / tests, mêmes règles de version et de release. Le code commun (réglages JSON, localisation `{l:Str}`, thème, dialogues, capture d'écran du test de fumée) est repris de Quai, pas réécrit.
- 2026-11-19 : affichage des pages par le **moteur PDF intégré à Windows** (`Windows.Data.Pdf`) — natif, déjà présent sur tout Windows 10 / 11 (rien à embarquer), aucun navigateur ni application web cachée. Écarté : PDF.js / WebView2 (interdit du projet). PDFium a été ajouté ensuite pour le texte seulement (voir plus bas).
- 2026-11-19 : modifications par **PDFsharp** (MIT) dans `QuaiPdf.Core` — bibliothèque .NET de référence pour réécrire un PDF (pages, rotation, import d'un autre document, propriétés), multiplateforme donc testée sous Linux comme sous Windows. Écartés : iText (AGPL), PdfPig (lecture d'abord, écriture limitée), QuestPDF (création seulement).
- 2026-11-19 : PDFsharp **figé en 6.2.4** — dernière version publiée sous MIT ; les versions 6.5.0 et 7.0.0-preview-2 (octobre 2026) sont sous AGPL-3.0, incompatible avec la licence MIT de Quai PDF. Toute montée de version passe par Alexandre.
- 2026-11-19 : `System.Security.Cryptography.Pkcs` référencé directement en 10.0.15 — PDFsharp 6.2.4 tire la 8.0.1, qui a des failles connues (GHSA-2fmv-rv2c-59x7, GHSA-846f-f764-76mx).
- 2026-11-19 : chaque modification part du contenu affiché (octets) et en produit un nouveau (`PdfOperations`, fonctions pures) — l'historique annuler / rétablir se résume à garder les contenus précédents (`PdfHistory`, 30 étapes), l'affichage montre exactement ce qui sera enregistré, et le fichier d'origine n'est touché qu'à l'enregistrement. Contrepartie : chaque opération relit le document (quelques dixièmes de seconde sur un gros fichier), faite en arrière-plan.
- 2026-11-19 : enregistrement atomique (`AtomicFile` : fichier temporaire dans le même dossier puis remplacement) — un PDF n'est jamais laissé à moitié écrit.
- 2026-11-19 : documents chiffrés ou protégés contre la modification = **lecture seule** — PDFsharp ne réécrit qu'avec le mot de passe du propriétaire, et réenregistrer risquerait de retirer la protection sans que l'utilisateur le sache. Le mot de passe d'ouverture n'est gardé qu'en mémoire, pour l'affichage.
- 2026-11-19 : un fichier que Windows affiche mais que PDFsharp ne sait pas relire reste lisible, en lecture seule — le moteur d'affichage décide de ce qui s'ouvre, PDFsharp seulement de ce qui se modifie.
- 2026-11-19 : tailles des pages données par Windows (`PdfPage.Size`, pixels à 96 ppp, rotation comprise) ; le test de fumée vérifie qu'elles égalent celles calculées avec PDFsharp (zone visible, rotation).
- 2026-11-19 : pages affichées dans un `ItemsRepeater` (virtualisé) et vignettes dans une `ListView` (sélection multiple, glisser-déposer pour réordonner) ; les images sont dessinées à la demande, seulement pour les pages à l'écran, deux à la fois au plus, plafonnées à 16 millions de pixels par page.
- 2026-11-19 : « Ouvrir avec » pour les `.pdf` déclaré par l'installateur (`OpenWithProgids`, par utilisateur) — Quai PDF ne prend jamais la place du lecteur par défaut : Windows laisse ce choix à l'utilisateur.
- 2026-11-19 : **sélection et copie du texte** (demande d'Alexandre) avec **PDFium**, le moteur PDF de Chrome, par les paquets `bblanchon.PDFium.Win32` / `.Linux` (binaires officiels de pdfium-binaries, Apache-2.0, x64 et arm64) — le moteur de Windows (`Windows.Data.Pdf`) ne donne que des images. PDFium fournit tout ce qu'il faut à la sélection : caractère sous le pointeur, rectangles à surligner pour une plage, texte d'une plage avec ses fins de ligne, ordre de lecture, droit de copie. Seule une quinzaine de fonctions de son API C publique sont déclarées (`PdfiumNative.cs`) : pas de « wrapper » (PDFiumCore n'est plus mis à jour). Écarté : PdfPig (il aurait fallu écrire nous-mêmes l'ordre de lecture et la logique de sélection).
- 2026-11-19 : l'affichage reste au moteur de Windows (déjà en place et vérifié par le CI) ; PDFium ne sert qu'au texte. Les deux lisent la même géométrie (zone visible, rotation) : le test de fumée vérifie que les tailles concordent, les tests vérifient le texte sur des pages tournées de 0, 90, 180 et 270°.
- 2026-11-19 : sélection comme dans un navigateur : appuyer puis glisser (même depuis la marge), double-clic pour un mot, Maj+clic pour étendre, Ctrl+A / Ctrl+C, menu du clic droit ; un simple clic n'en fait pas (sélection vide). Le curseur se place devant ou derrière le caractère le plus proche, cherché d'abord sur la même ligne. Le droit « copier le texte » du document est respecté, comme dans Edge et Chrome.
- 2026-11-19 : surlignage dans une `Canvas` à l'échelle 100 %, agrandie par une `Viewbox` : aucun recalcul au changement de zoom.
- 2026-11-20 : **mises à jour comme dans Quai** (demande d'Alexandre) — le code de Quai est repris tel quel (`Updates/` : source GitHub `releases/latest` sans jeton, comparaison SemVer avec le paquet `Semver`, téléchargement vérifié par SHA-256 avec le `digest` publié par GitHub, `UpdateBannerViewModel`, et ses ~50 tests), seuls le dépôt (`memton80/quai-pdf`) et les noms d'installateurs (`QuaiPdf-Setup-x64.exe` / `-arm64.exe`) changent. Même installation : Inno Setup en silencieux avec `/RELAUNCH=1`, relance par `--after-update`, réglage `checkForUpdates` pour couper toute connexion.
- 2026-11-20 : différence avec Quai : avant d'installer, Quai PDF propose d'enregistrer le document modifié (au lieu de fermer des sessions SSH) ; « Annuler » laisse la mise à jour en attente, déjà téléchargée. Le chemin du document ouvert est noté dans `updates/reopen.txt` et la nouvelle version le rouvre une fois (le CI le vérifie).
- 2026-11-19 : CI déclenché sur toutes les branches (Quai : `main` et pull requests) — le travail se fait sur des branches de développement ; seule `main` publie une release.
- 2026-11-20 : la sélection d'une seule page dans les vignettes **suit la page visible** (la barre de sélection montre où l'on en est, comme dans Edge ou Acrobat) ; une sélection de plusieurs pages, faite pour une commande, n'est pas défaite par le défilement. La page visible est mise à jour pendant le défilement (pas seulement à la fin), la dernière page devient la page visible tout en bas du document, et un « aller à la page » sans défilement (page déjà à l'écran) ne bloque plus le suivi.
- 2026-11-20 : **barre d'outils en boutons arrondis de Windows 11** (demande d'Alexandre, sur le modèle de « Redémarrer maintenant » des réglages de Windows) au lieu de la `CommandBar` et de ses icônes carrées : `Button`, `ToggleButton` et `DropDownButton` standard de WinUI, 32 px de haut ; « Enregistrer » est le bouton principal, en couleur d'accent avec sa flèche de menu. Ce bouton en deux parties est fait de deux boutons `AccentButtonStyle` joints : WinUI n'a pas de style d'accent pour `SplitButton`, et le surcharger aurait changé tous les `SplitButton` de l'application. Contrepartie : plus de menu de débordement automatique, la barre défile horizontalement si la fenêtre est trop étroite.
- 2026-11-26 : **refonte de l'interface, « piste C »** (choix d'Alexandre parmi trois propositions) : onglets dans la barre de titre (`TabView` de WinUI, un document par onglet, comme le Bloc-notes et l'Explorateur de Windows 11), rail d'icônes à gauche pour les volets (pages, plan, recherche, propriétés), barre de commandes allégée (boutons plats, « Enregistrer » reste le bouton d'accent, commandes de pages moins courantes dans « Plus »), barre d'état (page, état du document, curseur du zoom). Choix structurant : plusieurs documents ouverts dans une même fenêtre.
- 2026-11-26 : onglets gérés par `WorkspaceViewModel` (cœur, testé) : chaque onglet a son `DocumentViewModel` (historique, texte, recherche) et sa `DocumentView` gardée en mémoire tant que l'onglet est ouvert (position de lecture conservée) ; seule la bande des onglets est dans le `TabView`, les vues sont en dessous. Ouvrir réutilise l'onglet d'accueil vide, un fichier déjà ouvert sélectionne son onglet, fermer le dernier onglet revient à l'accueil. Instance unique : voir plus bas.
- 2026-11-26 : raccourcis posés une fois sur la fenêtre et appliqués à l'onglet affiché (une vue masquée ne doit jamais recevoir une commande) ; dans un champ de saisie, `Ctrl+A` / `Ctrl+C` / `Ctrl+Z` / `Ctrl+Y` restent ceux du champ.
- 2026-11-26 : **plan du document** lu par PDFium (`FPDFBookmark_*`, destination ou action « aller à ») : PDFium est déjà là pour le texte ; lecture bornée (profondeur, nombre d'entrées, boucles) contre les plans abîmés. Le type C `unsigned long` est déclaré `CULong` (32 bits sous Windows, 64 sous Linux).
- 2026-11-26 : **recherche** sur le texte lu par PDFium, avec la comparaison linguistique de .NET (`CompareInfo.IndexOf`, sans tenir compte des majuscules, des accents ni de la largeur) plutôt que `FPDFText_Find*` de PDFium, qui ne sait pas ignorer les accents. Une fin de ligne vaut une espace (trait d'union conditionnel ignoré par la comparaison, les positions restent celles de PDFium). L'occurrence montrée devient la sélection de texte : surlignage et copie réutilisent l'existant.
- 2026-11-26 : volet latéral : le réglage `showThumbnails` (nom gardé pour les fichiers de réglages existants) dit si le volet est ouvert, `sidePanel` lequel ; le volet est commun aux onglets.
- 2026-11-26 : **instance unique** (demande d'Alexandre) avec le cycle de vie du Windows App SDK (`AppInstance.FindOrRegisterForKey`, `RedirectActivationToAsync`, méthode documentée par Microsoft) plutôt qu'un tube nommé maison : un second lancement transmet sa ligne de commande au Quai PDF ouvert (qui ouvre les PDF en onglets et passe au premier plan) et s'arrête. Point d'entrée dans `Program.cs` (`DISABLE_XAML_GENERATED_MAIN`). Les tests du CI, qui isolent leur dossier de données, ont leur propre clé : ils ne parlent jamais à un Quai PDF ouvert par l'utilisateur.
- 2026-11-26 : la recherche est relancée d'elle-même après une modification, une annulation ou un rétablissement (les positions trouvées changent), sans déplacer la lecture.
- 2026-11-26 : **zones de texte** (demande d'Alexandre : écrire sur un PDF, et modifier les zones ajoutées dans Firefox ou Chrome) = annotations `/FreeText` (ISO 32000-1, 12.5.6.6), le format qu'écrivent Firefox, Chrome, Edge et Acrobat. Lecture par PDFium (rectangle affiché dans le même repère que la sélection de texte, `/Contents`, `/DA`, drapeaux), écriture par PDFsharp comme les autres modifications.
- 2026-11-26 : zones de texte toujours écrites **avec une apparence** (`/AP`) : Chrome et Edge (PDFium) ne dessinent que l'apparence, et ne savent pas la fabriquer pour une zone de texte. Elle est en **Helvetica WinAnsi**, l'une des 14 polices standard (rien à intégrer, connue de tous les lecteurs ; c'est aussi ce que fait Firefox), avec les largeurs publiées par Adobe (Helvetica.afm, relevées dans les tables de ReportLab, `Pdf/Helvetica.cs`) pour donner à la zone la taille de son texte. Contrepartie : les caractères hors Windows-1252 apparaissent en « ? » dans l'apparence ; le texte exact reste dans `/Contents`. Écarté : intégrer une police TrueType avec PDFsharp (fichier de police à trouver sur chaque machine, tests sous Linux impossibles sans police).
- 2026-11-26 : sur une page tournée, l'apparence porte la rotation inverse dans sa matrice (comme Firefox) pour que le texte reste droit à l'écran ; le passage des coordonnées affichées à celles du PDF (zone visible et rotation) est fait par PDFsharp et vérifié par les tests : chaque zone ajoutée est relue par PDFium au même endroit et dessinée par PDFium (rendu en image) droite et dans son rectangle, pour les rotations 0, 90, 180 et 270° et une zone visible décalée. Le test de fumée vérifie que le moteur de Windows dessine aussi l'apparence.
- 2026-11-26 : modifier une zone garde tout ce qui ne dépend pas du texte (nom, auteur, dates de création, bulle) et retire le texte enrichi d'Acrobat (`/RC`), qui ne correspondrait plus ; `/DA` et `/DS` sont réécrits. Les verrous de l'auteur sont respectés (`ReadOnly`, `Locked`, `LockedContents`) ; une zone avec ligne de rappel (`/CL`) est affichée mais ni modifiée ni déplacée, son apparence ne serait pas refaite à l'identique. Supprimer une zone supprime aussi sa bulle (`/Popup`) et les réponses qui s'y rattachent (`/IRT`).
- 2026-11-26 : une zone n'est jamais coupée automatiquement : une ligne de texte = une ligne de la zone, qui prend la taille de son contenu (comme dans Firefox) ; l'éditeur posé sur la page (police Arial, proche d'Helvetica) ne coupe pas non plus. Un texte vidé supprime la zone.
- 2026-11-26 : bouton **« Idée ou bug »** repris de Quai (`Feedback/FeedbackIssue.cs`, `FeedbackViewModel`, `FeedbackDialog`, `FeedbackSender`) : formulaire dans l'application, puis page « nouvelle issue » de GitHub pré-remplie dans le navigateur (formulaires `.github/ISSUE_TEMPLATE/*.yml`, champs remplis par l'adresse). Aucune connexion de Quai PDF lui-même, pas de jeton : l'utilisateur relit et publie.
- 2026-11-26 : champ de recherche : le texte indicatif d'un `AutoSuggestBox` n'est ni coupé ni abrégé et passait sous la loupe ; il est raccourci (« Rechercher (Ctrl+F) »), le libellé complet est dans l'info-bulle.
- 2026-11-26 : **surligneur** = annotations `/Highlight` (ISO 32000-1, 12.5.6.10), le format qu'écrivent Acrobat, Firefox, Chrome et Edge. Écriture par PDFsharp (`Pdf/PdfHighlights.cs`), relecture par PDFium (`FPDFAnnot_GetAttachmentPoints`). Toujours une apparence : aplats en fusion `/Multiply` (la couleur teinte le papier, l'encre reste noire, comme un surligneur fluo), dans le repère du PDF (aucune rotation à gérer). `/QuadPoints` dans l'ordre de fait des lecteurs (haut gauche, haut droite, bas gauche, bas droite) plutôt que celui, ambigu, de la norme. Les rectangles sont ceux de la sélection de texte affichée (PDFium) : le surlignage tombe exactement là où l'utilisateur a vu sa sélection. Les tests vérifient au rendu PDFium que le texte reste lisible sous la couleur, le test de fumée la même chose avec le moteur de Windows.
- 2026-11-26 : couleurs du surligneur claires et vives (jaune, vert, bleu, rose, orange) ; la couleur d'un surlignage existant n'est pas relue (PDFium refuse `FPDFAnnot_GetColor` sur une annotation qui a une apparence) : le menu montre la couleur des prochains surlignages.
